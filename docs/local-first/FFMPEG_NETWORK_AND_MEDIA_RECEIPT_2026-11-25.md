## 2. 网络问题：观察与结论分开

只读取了系统标准 HTTP/HTTPS/SOCKS 代理字段、相应本机端口连通性、目标 DNS/路由，以及公开依赖站点的 HTTPS 响应。未读取代理账号、订阅、配置密钥或其他应用凭据，未改变系统代理、节点、DNS、TUN、证书或安全设置。

| 测试 | 首轮 | 复测 |
| --- | --- | --- |
| 不显式指定代理：GitHub 公共接口 | HTTP 200 | HTTP 200 |
| 不显式指定代理：PyPI 公共元数据 | HTTP 200 | TLS 握手超时 |
| 不显式指定代理：构建站版本文本/ZIP 范围请求 | HTTP 200 / 206 | 两项均 TLS 握手超时 |
| 显式本机 HTTP 代理：构建站文本/ZIP、GitHub | CONNECT 200 后 TLS 握手超时，三项均失败 | 三项仍失败 |
| 显式本机 SOCKS5h：构建站版本文本 | HTTP 200 | HTTP 200 |

系统路由确认“不显式指定代理”仍经过本机 TUN，**不能称为绕过代理的物理直连**。端口可连接不等于代理外网链路健康。可复现的是 HTTP CONNECT 后的 TLS 停滞，以及其他出口的间歇性握手失败；仅凭这些测试不能断定具体远端节点、运营商或构建站中的哪一方是最终根因，也不是视频文件损坏导致下载失败。

原生下载先遇到 curl 35/28；改为 SOCKS 的整包尝试也失败，不能把一次 SOCKS 小请求成功说成已修复代理。浏览器打开 ZIP 另遭 `ERR_BLOCKED_BY_CLIENT`，属于客户端下载限制，不与原生 TLS 故障混为一谈。

本次可行绕行：仅对下载命令采用不显式指定代理、5 秒连接超时、80 秒单次上限、最多 4 次且包含 TLS 错误的重试，保留 HTTPS 校验、不跟随未知重定向、不换来源。随后两个整包下载均退出 0 并匹配固定哈希，分别约 6.837 / 12.489 秒。此前分块辅助下载只取得部分块；整包成功后已停止本任务自己的重复下载进程及子进程，保留其未完成记录，不冒称分块完成。

**本次依赖下载阻塞已绕过；系统代理及全网稳定性没有被修复或保证。** 成品运行不得依赖此联网绕行；下面的素材/渲染测试和模型服务另有进程级网络限制。
